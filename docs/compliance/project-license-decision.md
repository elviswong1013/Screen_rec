## 1. 当前事实

| 项 | 事实 | 证据 |
|---|---|---|
| `Cargo.toml` 声明 | `[workspace.package] license = "MIT OR Apache-2.0"`；`publish = false` | `Cargo.toml:20-21` |
| 子 crate | 各 crate 使用 `license.workspace = true`、`publish.workspace = true` | `crates/*/Cargo.toml`、`src-tauri/Cargo.toml` |
| 根许可证文本 | **缺失**：仓库根目录没有 `LICENSE`、`LICENSE-MIT`、`LICENSE-APACHE`、`COPYING` 或 `NOTICE` | 根目录列表；`git ls-files` |
| README | 没有许可证章节或授权说明 | `README.md` |
| 贡献者文件 | 没有 `CONTRIBUTING.md`、`CLA.md`、`AUTHORS` | 根目录列表 |
| Git 作者 | 当前历史仅见一个作者标识（不在此复述）；这不等于已确认版权归属/雇佣/外包关系 | `git shortlog -sne` |
| 当前发行状态 | 内部测试包，未签名、未清权；不是正式发行 | [ffmpeg-lgpl-package-report.md](../milestones/ffmpeg-lgpl-package-report.md) |
| 第三方义务 | FFmpeg LGPL-3.0-or-later sidecar；Tauri/Rust crates 各自许可证；WebView2/NSIS 各自条款 | [eula-draft.md](eula-draft.md) 第 7 条 |

**结论（工程事实）**：`Cargo.toml` 的 `MIT OR Apache-2.0` 是 SPDX 元数据声明，不是完整许可证文本；在没有根 `LICENSE` 的情况下，它不能清楚、完整地告诉接收者其实际权利。与此同时，如果对外按专有 EULA 分发，又与 `Cargo.toml` 声明冲突。**在决策完成前，不应对外宣称本项目是 MIT/Apache 开源项目，也不应把当前内部测试包当作已授权可分发的正式版本。**

## 2. 三种方案

> 以下为方案对比，不是推荐顺序；每种方案都需要律师按主体、市场、商业模式与贡献者情况审阅。

### 方案 A：开源（MIT / Apache-2.0）

**做法**：在根目录添加正式 `LICENSE`（MIT 或 Apache-2.0，或双许可 `MIT OR Apache-2.0`），保留 `Cargo.toml` 声明，补充版权行/第三方通知；如采用 Apache-2.0，评估 `NOTICE` 与专利授权条款。

| 维度 | 影响 |
|---|---|
| 客户权利 | 任何人可免费使用、复制、修改、合并、发布、分发、再许可/销售副本；必须保留版权与许可声明。Apache-2.0 另含明示专利授权与专利 retaliation 条款。 |
| 源码公开 | 源码可公开；修改者分发时需遵守许可证（MIT 要求保留声明；Apache 要求保留声明/NOTICE/变更说明）。不要求公开修改后的源码（非 copyleft）。 |
| 贡献者 | 外部贡献通常按 inbound=outbound 进入同一许可证；建议 DCO/贡献者声明，通常不需要 CLA（但需确认贡献者有权提交）。 |
| 第三方义务 | 不能覆盖 FFmpeg LGPL、Tauri/Rust、WebView2/NSIS 的许可证；仍需第三方通知、SBOM、源码 offer。 |
| 收费模式 | 不能阻止他人转售/商用/分支；收入可来自支持、咨询、托管、企业集成、培训、捐赠、品牌/服务，而不是“卖独占源码许可”。 |
| 主要风险 | 竞争对手可 fork；品牌/商标需另行保护；专利（AVC/AAC）与开源版权许可不是一回事；若包含不兼容的第三方代码，需清理。 |
| 适合 | 以 adoption/社区/生态为目标，接受源码公开与竞争。 |

**采用 A 时必须做**：
- 添加正式 `LICENSE` 与版权行；如双许可，明确 `MIT OR Apache-2.0` 的含义（用户可任选其一）。
- 保留 `Cargo.toml` 的 SPDX 声明并与 `LICENSE` 一致。
- 补充 `CONTRIBUTING.md`/DCO（建议）与贡献者版权确认。
- 第三方 notices/SBOM/source offer 不能省。
- 不能在 EULA 中限制 MIT/Apache 已授予的权利；如另有商业版，必须把开源版与商业版代码/品牌边界说清楚。

### 方案 B：专有商业 EULA

**做法**：不添加开源 `LICENSE`；将 `Cargo.toml` 的 `license` 改为与商业许可一致的表达或移除 SPDX 开源声明；使用经律师审阅的 EULA（参见 [eula-draft.md](eula-draft.md)）；补充贡献者版权转让/许可（员工、外包、自由职业者）。

| 维度 | 影响 |
|---|---|
| 客户权利 | 仅获得 EULA 明确授予的有限许可；不得再分发/转售/逆向工程（受法定例外限制）；可设设备/席位/期限/激活限制。 |
| 源码公开 | 源码不公开；需保护仓库/构建/密钥；客户可能要求源码托管（escrow）或安全审计。 |
| 贡献者 | 需确认所有代码版权归许可方；外部贡献需 CLA/版权转让，否则无法单方商业 relicensing。 |
| 第三方义务 | 仍须遵守 FFmpeg LGPL、Tauri/Rust、WebView2/NSIS；EULA 不能限制 LGPL 调试/替换/逆向权利。 |
| 收费模式 | 一次性许可、订阅、席位/设备、企业协议、维护/支持、激活/更新服务；需处理退款/撤回权/税费。 |
| 主要风险 | 执行/盗版/破解；消费者格式条款与责任限制的可执行性；未签名/未清权影响信任；开源社区可能不接受闭源分支。 |
| 适合 | 以付费闭源产品/企业客户为主，能承担 EULA、销售、支持与合规成本。 |

**采用 B 时必须做**：
- 不添加 MIT/Apache `LICENSE`；修改 `Cargo.toml` 的 `license` 字段，避免“元数据开源、实际闭源”的矛盾。
- EULA 律师审阅 + clickwrap + 版本归档；消费者/企业版条款可能不同。
- 贡献者版权链（员工/外包/第三方代码/AI 生成内容）审查。
- 第三方 notices/SBOM/source offer 不能省；LGPL 权利条款必须保留。
- 收费时补齐退款/撤回权/支付商/税务/发票。

### 方案 C：双许可 / 开放核心

**做法**：社区版按 MIT/Apache（或另选 copyleft，需另行评估）开源；商业版/企业功能按 EULA 闭源收费。常见组合：open core（核心开源、企业功能闭源）、双许可（同一代码对社区开源、对商业客户另售许可）。

| 维度 | 影响 |
|---|---|
| 客户权利 | 社区用户依开源许可证使用社区版；商业客户依 EULA 使用企业功能/商业版。边界必须在功能、代码仓库、安装包与文档中清晰。 |
| 源码公开 | 社区版源码公开；商业功能可闭源。需确保闭源代码不混入不兼容的开源代码，构建/仓库分离。 |
| 贡献者 | 若需将社区贡献用于闭源商业版，通常需要 CLA/版权转让或至少广泛的再许可授权；否则只能留在社区版。需明确贡献政策。 |
| 第三方义务 | 两版都要遵守第三方许可证；LGPL sidecar、WebView2、Rust crates 的通知/源码义务不因“社区版/商业版”而消失。 |
| 收费模式 | 企业功能、支持、SLA、托管、审计、SSO/管理、合规包、培训；也可对商业版收许可费。 |
| 主要风险 | 边界/治理复杂；社区可能认为“open core”不够开放；CLA 接受度；商标/品牌使用；两版安全修复同步；许可证兼容性。 |
| 适合 | 希望社区采用 + 企业变现，且能维护两版治理与贡献者授权。 |

**采用 C 时必须做**：
- 明确社区版/商业版的功能矩阵、仓库/构建边界、商标使用规则。
- 选择社区版许可证（MIT/Apache 或经评估的其他许可证）并添加正式文本。
- 贡献者 CLA/再许可授权（如商业版需要闭源使用贡献）。
- 商业版 EULA、企业 DPA、支持/SLA、价格/退款。
- 两版第三方 notices/SBOM/source offer 分别核对。

## 3. 方案对比速览

| 维度 | A 开源 | B 专有 | C 双许可/开放核心 |
|---|---|---|---|
| 源码公开 | 是 | 否 | 部分 |
| 可否转售/商用 | 通常可以（保留声明） | 需授权，通常禁止转售 | 社区版可以；商业版按 EULA |
| 是否可限制逆向 | 不能超出许可证/法律 | 可写限制，但受法定例外约束 | 社区版不能；商业版受法定例外约束 |
| 贡献者授权 | inbound=outbound；建议 DCO | 需版权转让/CLA | 通常需 CLA/再许可 |
| 收费空间 | 支持/服务/托管/品牌 | 许可/订阅/企业协议 | 企业功能/支持/托管/商业许可 |
| 竞争 fork | 难以阻止 | 法律+技术限制 | 社区版难阻止；商业版可 |
| 法律/运营成本 | 中（许可证合规/商标） | 高（EULA/销售/执行） | 最高（两版治理/CLA/品牌） |
| 与当前 `Cargo.toml` | 一致（补 LICENSE） | 冲突（需改 metadata） | 需拆分/明确 |

## 4. 决策所需问题

请负责人/法务逐项回答；未回答前不应选定方案或发布 operative LICENSE。

### 商业与客户

1. 主要客户是个人、企业，还是两者？首发市场是中国、美国、欧盟/EEA、英国、其他？
2. 收入模式：一次性买断、订阅、席位/设备、企业协议、支持/SLA、托管/云、培训/定制？是否收费仍未定？
3. 是否接受客户转售、fork、竞品基于本项目提供竞争产品？
4. 是否需要“开源社区版”作为获客/信任/生态手段？社区版与付费版的边界是什么？
5. 是否面向企业采购/政府/金融/医疗/教育？这些客户是否要求源码 escrow、SBOM、DPA、安全审计、签名、无障碍声明？

### 源码与贡献

6. 是否愿意公开全部/部分源码？公开后如何处理安全漏洞、密钥、构建脚本与内部文档？
7. 是否有员工、外包、自由职业者、第三方代码、AI 生成代码参与？版权/雇佣/外包合同是否已覆盖？
8. 是否接受外部贡献？采用 DCO 还是 CLA？CLA 是否允许闭源/双许可再分发？
9. 是否需要保留“闭源商业版”的代码隔离？如何防止开源代码与闭源代码/不兼容许可证混合？
10. 商标/品牌/Logo/域名是否已检索？是否允许社区使用 `Screen_rec` 名称/标识？

### 法律与风险

11. 目标市场对消费者 EULA、责任限制、退款/撤回权、仲裁/集体诉讼的要求？是否需要当地律师逐市场审阅？
12. AVC/H.264、AAC、`libopenh264`/`liblcevc-dec` 的专利许可/版税/报告义务是否会影响商业模式？收费/免费是否有区别？
13. 第三方组件（FFmpeg LGPL、Tauri、Rust crates、WebView2、NSIS）是否与拟选许可证兼容？是否需要替换/移除某些组件？
14. 是否需要专利 retaliation/专利池/防御性终止条款？Apache-2.0 的专利条款是否足够？
15. 出口管制/制裁、加密软件分类、最终用户/最终用途筛查是否影响许可证文本与市场？
16. 发生侵权/盗版/泄露/监管问询时，是否有预算与响应流程？是否需要产品责任/网络保险？
17. 未来融资/并购/资产出售是否需要清晰的 IP 归属与许可证审计？开源/双许可会不会影响估值/尽调？
18. 是否有历史承诺（文档、网站、安装包、Cargo.toml、README）需要纠正或向用户说明？

### 运营

19. 谁负责许可证合规（notices/SBOM/source offer/贡献者记录/商标续展）？预算与节奏？
20. 支持周期/EOL/安全更新承诺是什么？是否与许可证/收费模式匹配？
21. 是否需要自动更新/激活/许可证服务器？这会改变隐私政策、EULA 与数据流。
22. 中文/英文文本谁维护？版本如何归档？如何处理语言冲突？

## 5. 决策流程建议（不替负责人决定）

1. **事实盘点**：确认版权归属、贡献者、第三方代码、AI 生成内容、目标市场与收费模式。
2. **商业选择**：负责人在 A/B/C 中选方向；记录理由与放弃项。
3. **法律审阅**：中国律师 + 目标市场律师审阅许可证/EULA/消费者条款/专利/出口。
4. **工程落地**：仅在决定后添加正式 `LICENSE` 或修改 `Cargo.toml`；同步 README、About、安装包、第三方通知。
5. **贡献者政策**：按方案补充 DCO/CLA/版权转让；保留签署记录。
6. **发布验证**：用 [release-checklist.md](release-checklist.md) G1/G4 复核；归档许可证版本与接受记录。
7. **持续维护**：每次依赖/市场/商业模式变化时复核；不静默变更许可证。

## 6. 过渡期措施（在决定前）

- **不添加** operative `LICENSE`；不把 `Cargo.toml` 的 MIT/Apache 声明当作已生效许可对外宣传。
- 对外只使用“内部测试/评估”措辞；与测试者签署简短评估/保密条款（不作为正式 EULA）。
- 保留所有第三方 notices/SBOM/source offer 工作，不因项目许可证未定而延后。
- 如必须现在对外分发，先取得律师对“临时评估许可/保密协议”的书面意见；不要用本备忘替代。
- 记录当前 `Cargo.toml`/README/安装包中的许可证表述，决策后统一修正并保留变更记录。
